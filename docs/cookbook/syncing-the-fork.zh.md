# 同步个人 fork

[English](syncing-the-fork.md) | 中文

本指南用于在合入上游更新时保留本地行为。[现存偏差清单](../fork-deviations.zh.md)记录仍需本地维护的源码改动；已有的仓库测试、快照和包文档仍负责说明相应行为。

## 修改 fork 之前

1. 核对当前分支、工作区修改和两个远端地址。先保护未完成的工作，不移动或覆盖这些改动；日常分支不能直接用作上游集成区。
2. 分类本地改动：个人选择尽量使用 profile patch 或树外插件；无法通过扩展点实现的缺陷使用范围明确的源码修复；个人产品风格另行维护。保留上游作者和许可证信息，不能假定上游发布版包含本地行为。
3. 每项长期源码修复都在同一次改动中新增或更新清单条目，记录可观察的失败、行为回归测试、已知的上游 issue 或 PR 以及退出条件。安全且可行时，确认撤去修复后测试会失败；仅在两个实现叠加时通过的测试不能证明上游已修复。
4. 开发前识别受影响的产品：Web 和 Desktop 共享产品代码，但 Desktop 打包独立的精确版本运行时，需要分别验证。参阅 [Desktop 安装归属与发布要求](../../apps/desktop/README.zh.md)，不要用 Web 冒烟测试代替 Desktop 发布验证。

## 集成一个上游版本

1. 从官方上游获取更新至跟踪引用，并记录同步前后的版本。从已验证的日常分支创建独立的集成分支与 worktree。不要在带有未提交改动的日常工作区执行合并，也不要向上游远端推送。
2. 将选定的上游版本合入集成分支；正在处理冲突时，保留检查点，再考虑改用更新的上游基线。根据实际行为解决源码、生成文件和双语配对冲突，不能只看 Git 文本合并结果。配对记录发生冲突时，参阅[配对合并恢复步骤](../development.zh.md)。
3. 逐项审查[清单](../fork-deviations.zh.md)中的现存偏差，包括文件没有冲突的条目。合并后比较受影响的执行路径和配置；无冲突不等于修复仍然生效。对完整配置被 patch 覆盖的 profile 行重新核对字段。
4. 在集成后的代码上运行相关回归测试，再按[仓库测试规则](../testing.zh.md)选择覆盖上游新增变化的最小检查。模型或用户可见行为应纳入相应快照与真实组合测试。记录实际运行的检查；没有运行不能记为通过。
5. 如果上游似乎修复了清单中的缺陷，先在集成分支移除本地实现，再运行原有行为测试。只有撤去补丁后该测试及相关集成检查仍通过，才能将条目退出；保留测试，或指出上游等效的回归保护。缺少证据或行为退化时，不得推进集成。
6. 只有每个现存条目都有结论，才将已验证的集成结果更新到日常分支。保留合并检查点，供下次比较版本；不要只为隐藏上游合并记录就重排已发布的日常分支历史。

## Desktop 验证

Web 和 Desktop 共享应用行为，但 Desktop 独立管理 profile、匹配的打包运行时、平台依赖、签名和更新检查。仅影响 Web 的修复也需要评估 Desktop 影响；运行时、Electron、打包、原生模块、安装或更新的改动，需要运行 [Desktop 开发与打包文档](../../apps/desktop/README.zh.md)所述的针对性检查。不要把 fork 构建称为上游官方签名的 Desktop 版本，也不要认为本机打包覆盖所有平台。

## 验证就绪状态

只有本地源码差异的清单盘点完整、每项现存行为回归测试在合并结果中通过、退出的条目在没有本地修复时仍通过、相关产品检查通过，而且候选分支没有混入未完成工作，集成结果才算就绪。当前清单明确尚未盘点完成；宣称上游同步已验证前，必须补齐基线。
